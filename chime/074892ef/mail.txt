What can we learn from the idea that Ranges may actually be traversed using Iterator (Consumer driven) or using Generators (Producer driven)?

	==> Also see “Todo: Programming - Consider to argue that Generators reflect structure in code whilst Iterators reflect structure in state?"

1) This seem like a good talk by Arno Schöld where this idea is presented and explained (https://www.youtube.com/watch?v=vrCtS6FDay8 <https://www.youtube.com/watch?v=vrCtS6FDay8>)?

	==> The Iterator concept means the Consumer is at bottom of stack calling the Iterator for Range members.

		==> Iterator must carry state and can’t use stack variables for storage.
		==> Iterating complex structures can be close to impossible and inefficient (restore state on each call)

	==> The Generator concept means the Producer (generator) is at bottom of stack calling the Consumer with Range Members.

		==> Generators can traverse structure in code (“State” mirrored in code)
		==> Generators can use stack variables.
		==> Consumer can be cheap to call (only need to act on provided range member)

2) What can we say from comparing different prominent “Range” related C++ concepts?

	==> Consider Arno Schöld idiom and think-cell open source range library on github (https://github.com/think-cell/range <https://github.com/think-cell/range>)?

		==> At 4:30
			==> Conatiners are Ranges (owns elements, deep copying, deep constness)
			==> Views are basically begin/end iterator pairs (don’t own elements, shallow copying, shallow constness)

		==> At 6:30
			==> Range Adaptors (More interesting Views)
			==> Example “adapting” a Range of records into a Range of int members of each record.
			==> The Adaptor Range is lazy so nothing is created (adaption happens on access, i.e. the referenced record member int is returned).
			==> The Adaptor has a member base() that returns a reference to the “un-adapted” element reference (in this case the record)

		==> At 12:20 Key Point of self-sufficient adaptors creating large storage overhead.
			==> adaptor of adaptor of adaptor replicates functor and iterators (each adaptors self-sufficient)
			==> Boost::Ranges does this.

		==> At 13:20
			==> Enhance by having iterator point to range and base iterator
			==> Adaptor only carry common functor and end iterator.
			==> Consequence - Iterator life span restricted to Range life-span.
			==> State-of-the-art (Nibblers Range v3 does this)

			==> Still not great (still linear overhead)

		==> At 14:15 - The “Index” concept.
			==> All Index operations gets the Range as input (enables single storage location of Range)
			==> An Index-range uses Index as Begin/End (removes need to store self-sufficient iterators)
			==> Add increment/decrement index to the index range.
			==> Possible to co-exist with the “world” of Iterator Ranges.

			==> Key point - The Index type can be shared by base range and adapted range.

		==> At 20:11 - think-cell rvalue handling
			==> v3 does not allow creating a view to a temporary created range (the view must reference an existing range)
			==> think-cell ranges aggregates (move) the container when provided a temporary one (called with rvalue)
			==> think-cell range thus remains lazy.
