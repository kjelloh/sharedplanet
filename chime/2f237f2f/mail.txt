2) Consider the high lights of this talk?

	==> Go uses “Duck Typing” that seems to be type inference where the inferred type only contains the stuff you really use?

		==> It seems with Duck Typing you can use objects through an interface as long as they implement the part of the interface you are really using?
		==> It like “if it behaves like a Duck we can treat it as a Duck” (The Duck being what we actually call)?
		==> See wikipedia on Duck Typing (https://en.wikipedia.org/wiki/Duck_typing <https://en.wikipedia.org/wiki/Duck_typing>)?

	==> Go seems to allow structs to be defined with unnamed members (at 30:26 into https://youtu.be/zJVtpkxq_X0?t=1826 <https://youtu.be/zJVtpkxq_X0?t=1826>)?

		==> In Go “Embedding” seems to mean I define member types without naming them - and still be able to access members members (that is named)?

		==> So, having these types…

 			

		==> I can Embed these types unnamed in a struct (Note members have no names but the types are known)...

			

		==> I can still instantiate an Embedding struct (only type constructors. i.e. type names, required for this)

			

		==> And now I can still access the members members either using embedded type names - or by inferring type names through using accessed type member names?

			

			==> Note: Go uses “:=“ to mean type inference (e.g., like auto in C++)?
			==> Thus, x := r.Point.X refers to member X of r’s member with type Point.
			==> And x := r.X means The member named X of the member in r that has such a member name?
