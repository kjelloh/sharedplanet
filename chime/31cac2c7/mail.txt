2) Consider this blog post explaining Move Semantics, temporaries and rvalues (http://www.cprogramming.com/c++11/rvalue-references-and-move-semantics-in-c++11.html)?

	==> Consider a rvalue reference is a mutable reference to a temporary (as an extension to C++03 immutable const& to temporaries)?

const string& name = getName(); // C++03
string&& name = getName(); // C++11

		==> In > C++11 the compiler will detect that getName returns by value (thus it is a temporary) and treat it as an rvalue reference (T&&)
		==> Thus, name being T&& is allowed to bind to the returned temporary (keeping it alive)

	==> Consider in C++ we can overload on T& or T&& to guide the compiler to generated different code?

printReference (const String& str) {
        cout << str;
}
 
printReference (String&& str) {
        cout << str;
}

	==> And this gets useful to write special constructors and assignment operators for rvalues (temporaries)?

    / move constructor
    ArrayWrapper (ArrayWrapper&& other)
        : _p_vals( other._p_vals  )
        , _size( other._size )
    {
        other._p_vals = NULL;
        other._size = 0;
    }

		==> As we know this code is for treating a reference to a temporary we are free to “steal” its content (no-one will get sorry)
		==> Note how we are allowed to mutate the “moved-from” object to indicate the sealed data (nullified pointer)

	==> It seems we can understand that a defined rvalue reference (named) is actually an lvalue in its scope!

“in our constructor, the object has a name; it will be alive for the entire duration of our function. ... the temporary object has a defined location that truly persists for the entire function. It's an lvalue in the true sense"

	==> Thus we have to convert it back to an rvalue if we like to pass it on as such.

MetaData (MetaData&& other)
    : _name( std::move( other._name ) ) // steal other.name
    : _size( other._size )
{}

	==> It seems we benefit from understanding when the compiler stops generating default constructors?

“As you know, in C++ when you declare any constructor, the compiler will no longer generate the default constructor for you. The same is true here: adding a move constructor to a class will require you to declare and define your own default constructor. On the other hand, declaring a move constructor does not prevent the compiler from providing an implicitly generated copy constructor, and declaring a move assignment operator does not inhibit the creation of a standard assignment operator."

		==> So, adding any constructors inhibits compiler generated default constructor (but default copy constructor is still generated)?
