3) It seems the ”pipe” operator is used to chain asynchronous event stream transforming actions and kick of processing by the last function being a ”subscriber” to the chained functions?

	==> It seems ”function” chained by the pipe-operator creates a new ”stream” - in effect making processing ”lazy” (nothing happens until the created function is actually called)
	==> It seems it is the last function in the chain (the subscriber) that implements the actually calling (staring to process the stream)?

4) It seems we need to kick-of the stream chaining by create-and-publish an observable (that may then be chained into new published observables)?

	==> Consider this example (

int main() {
    auto keys = rx::observable<>::create<int>(
        [](rx::subscriber<int> dest){
            for (;;) {
                int key = std::cin.get();
                dest.on_next(key);
            }
    }).publish();
    auto a = keys.filter([](int key){return std::tolower(key) == 'a';});
    auto g = keys.filter([](int key){return std::tolower(key) == 'g';});
    a.merge(g)
        .subscribe([](int key){
            std::cout << key << std::endl;
        });
    // run the loop in create
    keys.connect();
    return 0;
}

		==> It seems keys.connect() initiates observation of the published observable keys ( rx::observable<>::create<int> … .publish())?
	==> It seems merge is a standard algorithm and thus a member of each observable stream (in this case stream a)?

		a.merge(g) // creates a merged observable stream of a and g?
