It seems like a good idea to use a C++ template syntax Value<n> for level dependent Value types and have standard member functions as_function, as_value and as_text to define implementation?

1) It seems most Values can be defined by specifying them on three relative meta layers 2, 1 and 0?

	==> Consider Value<2> would refer to an Atomic value that constructs Value<1> instances from Value<1> argument?
	==> Consider Value<1> would refer to an intermediate Composite (or Atomic) that constructs Value<0> from Value<0> argument?
	==> Consider Value<0> would refer to a Composite (or Atomic) on terminating meta-layer?

2) Consider each Value Implementation has member operations as_function, as_value and as_text?

	==> Consider Value<2> would refer to an Atomic value that constructs Value<1> instances from Value<1> argument?
		as_function = Constructs Value<1> from argument Value<1>
		as_value = self
		as_text = script representation of value
	==> Consider Value<1> would refer to an intermediate Composite (or Atomic) that constructs Value<0> from Value<0> argument?
		as_function = Constructs Value<1> from argument Value<0>
		as_value = self
		as_text = script representation of value
	==> Consider Value<0> would refer to a Composite (or Atomic) on terminating meta-layer?
		as_function = ErrorValue or forward to function definition (if function value)
		as_value = self
		as_text = script representation of value

3) Consider how this relates to Lisp syntax (name names) evaluates to (as_function(name) as_value(names)) and name evaluates to as_value(name)?

	==> Consider identifier-list evaluation?

		evaluate(list) = evaluate(as_function(head list) as_value (tail list))?

	==> Consider identifier evaluation

		evaluate(identifier) = as_value(identifier)

	==> Consider as_text is used to produce text representation to communicate with humans?

		==> Consider REPL print?

		evaluate(expression) ==> as_text(evaluate(expression))?
