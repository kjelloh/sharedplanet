4) Consider the signal design of asynchronous view update interface?

	==> Should the model register view-Ids to know where too post updates?
	==> Should the front-end provide a single-sink and dispatch messages to adressed views?
	==> In what ways can we imagine to short-cut update messages from each data model member to its corresponding view?
	==> Consider to what degree we should aggregate larger ”chunks” of model members to reduce update messaging to the cost of sending larger chunks of data?
		==> E.g., is it more efficient to send update of the whole visible part of a list rather than only the member that changed value?

	==> Should we consider data structure changes to be more expensive to update than unstructured value changes?
		==> E.g., it seems updating the view to show adding a child to a tree node affects the view more than just changing a tree node value?
		==> On the other hand, we can’t know if the added child node results in a visible change?
		==> And the change of an unstructured data value may also result in a structural change in the view (if the value represents visible or structural information)?
