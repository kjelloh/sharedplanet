Can we gain anything from discussing what traits we would like a C++ Protocol Framework should have to enable some “easy” way of implementing popular protocols?

1) A Protocol seem to be a combination of “message” and “Behaviour”?

2) A protocol seem to define a sender and a receiver side?

3) Many protocol seem to define a “Client” role (initiating messaging session) and a “Server” role acting on client initiatives?

4) Protocol Messages seem to combine “Encoding" and “Implication”?

5) Many protocols are “Stack-able” or represent stacks of sub-protocols (e.g. TCP/IP)?

6) A protocol is a “Messenger” that exchange “Cargo” with the “Other Side”?

	==> This reflects the fact that a protocol defines how to talk end exchange data with another actor?

7) A Protocol may be implemented as a black-box “Messenger" that transfers “Cargo” to and from the “other side”?
 
	==> This implies that if one stacks Messengers one get a new Messenger?

8) Protocol Message Representation often require “Cargo” to be obtained and deposited as sub-elements?

	==> This reflects the fact that protocols assigns “Implication” to defined elements of Messages (e.g. Header and Cargo Elements of SPDH)
	==> BERTLV is an “neutral” encoding format often used by a Protocol to identify tagged elements as having defined implications (and thus content)

9) All Protocols define “Streams” of bits often grouped into octets or other range lengths?

10) It always makes sense to talk about “Downstream” and “Upstream” messaging?

	==> Downstream Messaging always meaning from server (responder) to client (requester)?
	==> Downstream Messaging within a local Stack always means towards the bitstream sender actor?
	==> Confusing: This would mean Stackwise Downstream is in the direction of Message Upstream for Client sender?!
		==> Client Stack Downstream corresponds to Server Stack Upstream and both to Message Upstream!

	==> Consider to find better terms to refer to Node-to-Node Messaging direction and Layer-to-Layer Stack direction?

	==> The element-key-path uniquely defines message Elements and is strongly typed by the Protocol.
