It seems, if we view data encoding as consisting of structure encoding and value encoding, that the tag-path-based design should allow for both explicit (encoded) and implicit (element identification based) value processing?

1) Consider the basic mode to be processing of data structures using tag-path-based element processing without value encoding information?

	==> Consider at basic level the only information provided for element processing is the element tag path and wether it is a primitive or a composite element?

		{tag path, composite}
		{tag path, primitive}

2) Consider element value encoding to be an optional additional level of processing?

	==> Consider for a primitive node, additional type::representation may be provided in processing?

		{tag path, primitive, type::representation}

		==> Consider type to define “what” e.g., boolean, integer or text?
		==> Consider representation to define “how” e.g., boolean::octet, integer::octets, text::utf-8 (i.e. type plus encoding)?
		...
		
	==> Consider it is only “primitive” (unstructured) values who’s encoding is defined (composite elements are processed on structure information only)?

	==> Consider a value to be defined as “what” it represents (its type) and “how” it is represented (its encoding)?

		==> Consider “what” to be some standard set of types as Boolean, Integer, Float or Text?
		==> Consider “How” to be defined by a “codec”, “Encoding” or “Representation”?

			
			==> Consider C++ memory representation of primitive data types to be one sort af value encodings (including endianness)?
			==> Consider ISO-OSI 7-layer “Representation” layer to be about encoding (representing) values?
			==> Consider to define some canonical way to represent values as Text or in some binary form?
			...
			==> Consider that XML, HTML, BERTLV does NOT define how to encode values (They define how to encode structures and requires implicit knowledge of value encodings)?

3) Consider that by separating structure encoding from value encoding the model melts down to something really simple?

	==> Consider the number of structures imaginable is actually quite small to cover all composite structures?

		a) Unstructured (Primitive)
		b) Structured (Composite)
			|
			|
			— Fixed or variable set of members, Fixed or variable sized Members, Ordered or unordered members

	==> Consider the ways to encode structure is also quite small?

		a) Pre-fix encoding (each element is prefixed to encode structure)
		b) Element separation (each element is separated with a separator encoding)
		c) Element framing (each element is encoding using most a prefix and post-fix, e.g. XML elements)
		c) Structure mirroring values (dedicated element value, e.g. a bitfield, defines the encoded structure, e.g. ISO 8583 bitfields)
		d) Position based structure (Record or Array of elements each defined by its size and position)

	Consider the number of value types and representation is quite small

		a) Consider the types Boolean, Integer, Real and Text could cover all data types we need to encode?
		b) Consider the ways to encode these can be efficiently defined (including endianness) using a very small set?

			==> All data can be encoded into octets of bit streams?
			==> One endianness will suffice (and each platform must understand the endianness used)
			==> A boolean can be encoded as an octet with value 0 (false) and not false as true.
			==> An integer can be encoded as a stream of octets applying the same endianness as each bit stream.
			==> A Real number can be encoded using a defined sufficient way?
				==> Or do we need to enable optimisation as has been developed in gaming or 32 versus 64 bit platforms?
			==> A Text can be encoded in Unicode using UTF-8, UTF-16 or UTF-32?
			...
