6) So, how can we explain (understand) what the C++ standard proposal async-and-await idiom is doing behind the scenes (i.e. how do we ”read” the code)?

	a) A function/method is declared using the key-word ”async”.
		==> This is now a special method that is resumable
		==> It returns a future that will not be ready until the call related to that future has completed (hit its return statement)
	b) Inside such a function one may define ”await” statements.
		==> Each await-statement wraps the result of the statement into a future.
		==> The function ”returns” each time it initiates the processing of an await statement (behind the scenes it generates code to wait for the future returned from the statement)
	c) The client calling the async function will get the future returned from the function when it hits its first await (or its final return if no internal await is executed)
		==> So, from the callers point it will get a future that will be ready when the function executed all its internal ”await” statements and reaches a return statement.
	d) The compiler is now able to generate code that allows the async-function to execute concurrent calls without instantiating a spectate thread and call stack (large overhead)
		==> Instead it may optimize the concurrency on the same stack.frame using call-related heap-data and true core-dispatched processing)
