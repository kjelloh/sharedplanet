2) Consider to discuss encoding transparence of some gateway-paths?

	==> Consider to describe when EBCDIC —> ASCII —> EBCDIC “works” although the intermediate ASCII encoding is actually not correct (e.g. by following ‘Ä’)?

		Client Send: ASCII IEC 646 (swedish 7-bit ASCII) —>  EBCDIC 278 (Sw/Fin)
		Gateway: EBCDIC 037 (US) —> ASCII  (US 7-bit ASCII) —>  EBCDIC 037 (US) (http://www.easymarketplace.de/codepages.php)
		Server Receive: EBCDIC 278 (Sw/Fin) —> ASCII IEC 646 (swedish 7-bit ASCII)

		==> The Client will map ‘Ä’ to 0x5B as defined by ISO/IEC 646 (https://sv.wikipedia.org/wiki/ASCII) and then to 0x7B (http://www.easymarketplace.de/cp/cp00278_Finland_Sweden.pdf)
		==> The Gateway will decode 0x7B to ‘#’ (http://www.easymarketplace.de/cp/cp00037_US.pdf) to  0x23 (ASCII ‘#’)
		==> The Gatway then reverses this back to EBCDIC ‘#’ 0x7B ok.
		==> And the receiver decodes it using EBCDIC 278 and ASII IEC 646 to an ‘Ä’ ok.

		==> So, as long as the intermediate uses a unique 1-to-1 mapping it does not matter that the mapping is incorrect?
		==> It seems the intermediate (being a processor or acquirer) will run into problem if the text is parsed (or presented for human reading)?

			==> E.g. if the intermediate processing does not allow the character ‘#’ in the encoded text it will be a problem?
