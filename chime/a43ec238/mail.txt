So, could it be that what is missing from the C++ string handling is a way to easily use a Code Point View (Operations on Code Points) and a Meaning View (operations on the text meaning)?

1) Consider current strings are Code Unit Containers (arrays of Code Units)

	==> In Code Unit world escaped Code Point encodings will show in the data.
	==> Thus problem with current string handling operating on encoded text is at least two-fold?
		==> Two string values may carry different encodings?
		==> Two string data units may or may not be a Code Point (e.g. be part of an escaped Code Point)?

2) Consider to add a Code Point View that knows about what encoding that is used?

	==> Then such a view will be able to ensure operations on Code Point ranges?
	==> In this world the different encoding issue remains as different-coped-point-set issue?

3) Consider to add a meaning-view where texts may be operated on as defined by its IRL meaning (e.g. an ‘A’ is recognised as the same meaning regardless of Code Point Set)?

	==> In this world two texts meaning “Välkommen” is equal independent on what Code Point Set that use used?

4) So, what should we call the Code Point Set view and the Meaning View?

	==> Consider std::text should be the meaning view?

		std::text<UTF-8>(“Välkommen) == std::text<ISO-LATIN>(“Välkommen”)

	==> Consider std::code_points should mean a Code Point view?

		std::code_points<UTF-8>(“Välkommen”) <> std::code_points<ISO-LATIN>(“Välkommen”)

	==> Consider how we would like to add std::code_points and std::text to extend existing string literals and string classes?
