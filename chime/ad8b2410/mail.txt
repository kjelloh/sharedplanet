3) Consider the following design of iterative-range-mapping?

	==> Each iteration uses a rule to parse one range into a list of ranges.
	==> Each range in the list is in a touple together with an ID assigned by the rule (thus each “element” gets an ID)
	==> Each iteration ends with applying decodings to ranges as mapped from provided decoders and range-ids.
	==> Each range that is decoded results in creation of a new vector to hold decoded data and having the range changed to refer to decoded data.
	==> End result is a list of couples of ranges (each having an unique ID) and some referring to new (decoded) data.
	==> The list carries enabled or disabled ranges (disabled ranges used to remember ranges active on lower levels but now excluded)
	==> Each range has the same interface but may be a range of vector iterators to source data, a range of adapter iterators (performing byte-by-byte transform of source) or range of new (decoded) vector data).  

	==> Provide a special concatenate-iterator that “lifts” a list or ranges into a single range again
	==> The concatenate-iterator skips disabled iterators and iterates only through each active range in the list (making it appear as one range)

	==> Now the range-list produced by one iteration may be used as input to the next (using new rule and list of decodings)

template <typename ID, typename T, typename NextContext>
struct context {

	context(T const& val, NextContext const& next_ctx)
		: _val(val), _next_ctx(next_ctx) {}

	/**
	  * Explicit get of our T value (called with our ID).
	  * Compiler matches this for call to get(ID& id)
	  * boost::mpl::identity<ID> is eqvivalent to template <typename X> struct {typedef X type;} // http://www.boost.org/doc/libs/1_60_0/libs/mpl/doc/refmanual/identity.html <http://www.boost.org/doc/libs/1_60_0/libs/mpl/doc/refmanual/identity.html>
	  * Thus get() takes a parameter that is an empty struct that is default constructable only from ID (hides all other implicit type conversion to ID)
	  */
	T const& get(boost::mpl::identity<ID>) const {
		return _val;
	}

	/**
	  * Compiler always matches a call to get(NOT_ID& id) to this one (i.e. get called with type other than our ID)
	  * Compiler will instanciate a call to the matching get in _next.ctx.
	  *
	  * http://en.cppreference.com/w/cpp/utility/declval <http://en.cppreference.com/w/cpp/utility/declval>
	  *
	  */
	template <typename Identity>
	decltype(std::declval<NextContext>().get(Identity()))
	get(Identity id) const {
		/**
		  * This will expand to either
		  * 	_next_ctx.get(boost::mpl::identity<Identity>)
		  *		or template <typename Identity>	decltype(std::declval<NextContext>().get(Identity())) get(Identity id)
		  *
		  * The second will then expand the same way until the compiler finds a macthing get(boost::mpl::identity<Identity>)
		  *
		  * Compiler optimazation will then remove redundant code to create a direct call to the correct get in the chain...
		  *
		  * ==> (magic)!
		  *
		  * Note: The chain must end with the empty_context to ensure the compiler always finds a match if no context in the chain has a value to get for provided Identity
		  */
		return _next_ctx.get(id);
	}

	T const& _val;
	NextContext const& _next_ctx;

};

struct empty_context {
	struct undefined {};

	template <typename ID>
	undefined get(ID id) const {
		return undefined();
    }

};
