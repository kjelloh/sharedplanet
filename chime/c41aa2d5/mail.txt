Consider we can imagine a procedure where the sender of an invoice encrypts its name with its private key so that the receiver can check this using the senders public key?

1) Consider how the sender and receiver can cooperate to enable the receiver to authenticate received invoices (or other communication)?

	==> Consider the sender encrypts its name using its private key?
	==> Consider it then puts the encrypted data as BASE-64 on the sent invoice?
	==> Consider the sender publish its public key?
	==> Consider the receiver may now decrypt the BASE-64 encoded data with the public key?
	==> Not the receiver should get the correct sender name (if not, the sent invoice is a fraud)?

2) Consider to enhance the process so that only a Hash is exchanged?

	==> We need a way so that the sender can generate a hash that the receiver can authenticate ONLY using the public key?
	==> It seems the sender can first hash its name using a defined hash algorithm?
	==> The sender can even publish this hash?
	==> The sender then encrypts this hash with its private key?
	==> The result is data of the same length as the hash?
	==> The sender now sends this encrypted hash on the invoice to the receiver?

	==> The receiver now uses the public key of the sender to decrypt the received hash.
	==> The result should now be the hash of the sender?

	==> It seems the QR-code storage capacity of 2953 bytes vastly exceeds the RSA key length requirement of 256 bytes (we can store some additional info)?
