2) Consider that LSeq actually does NOT resolve the state into the correct one?

	==> Consider that although LSeq will make the state eventually consistent (but that state is not usable)?

		==> Also see “Todo: Darwinet - Consider to motivate survival-of-fittest-view with the argument that views always shows meaningful state where a merge algorithm will always create an invalid state?"

		==> The algorithm solves the problem that two or more actors delete and add text at the same location by protecting the order or these changes?
		==> But although the final merged state contains both the operations, the merged result is NOT what either actor intended?

		==> Se the example at 34:42 for LSEQ resolution of two conflicting edits to a text (https://youtu.be/pMMDVphop40?list=PL03Lrmd9CiGewi0lbnahxEpisoP5WZocX&t=1988 <https://youtu.be/pMMDVphop40?list=PL03Lrmd9CiGewi0lbnahxEpisoP5WZocX&t=1988>)?

			==> So, we have two conflicting edits by Alex and Beth
			Alex: “sandwich” -> “sandywich"
			Beth: “sandwich” -> “sandwhich”

		

		==> Which LSEQ handles as commutative operational transforms (character paths persist)

			==> I.e., LSEQ allows Alex:s and Beth:s edits in any order (the same end state will be produced)

		

		==> BUT - The end state is NOT what Alex not Beth intended!

			==> So, although the end state is consistent, Alex and Beth must still agree on what the true end result should be?

			Alex: “sandwich” ->	 	“sandywich"
			Beth: “sandwich” -> 	“sandwhich”
			--------------------------------------------
			=					“sandywhich"
