		==> Consider the cases where caller and callee are subrotuines, coroutines and goroutines?
		==> Consider we can make any combination work by applying appropriate messaging and activate,resume and yield implementations?

		==> It seems a subrotuine and coroutine share its state (its frame) with the caller?
		==> It seems a goroutine shares nothing with its caller?
		==> It seems subrotuines and coroutines uses the shared state to exchange messages with the caller?
		==> It seems gorotutines uses call and response channels to exchange messages?
 
	==> Consider S+A (Suspend+Activate) can be defined also also to activate a Coroutine and a Goroutine?

		call f(x) expands to:		caller::suspend —> message: x —> f::activate

		subroutine::suspend + coroutine::activate

			==> Works if we just apply the appropriate caller::suspend (store state in stack-frame)?
			==> In this case coroutine::activate must accept a heap-frame shared with the caller (coroutine must store its state to live on after yield)?
			==> Thus, the message: x must live in the heap-frame (its part of coroutine state) ?
			==> Note: A coroutine shares its state instance with the caller (used by caller to interact with coroutine)?

		subroutine::suspend + goroutine::activate

			==> Works if we just apply the appropriate caller::suspend (store in stack frame)
			==> In this case goroutine::activate must accept a channeled message
			==> Thus the goroutine gets its own copy of the message to store in its ”process” local memory?
			==> Note: A goroutine shares nothing with the caller (goroutine can be executing on completely remote hardware)

	==> Consider callee C+Y (Cancel and Yield) is trivial for coroutine and goroutine?

		f(x) {return result} expand to:	f::cancel —> message: result —> caller::resume

		coroutine::cancel + subroutine::resume

			==> Works if we just apply appropriate caller::resume (needs to accept final value on the shared heap-frame)
			==> It seems we require the caller to detect that the coroutine has canceled and thus delete the heap-frame (after having acquired the returned value)?

		goroutine::cancel + subroutine::resume

			==> Works if we just apply appropriate subroutine::resume (needs to accept a message copy from callee response channel)
			==> It seems we require the caller to detect that the goroutine has canceled and thus close the channel (after having acquired the return value)?
			==> Consider we may use a buffered stateful (open/closed state) channel that is garbage collected when it is empty and closed (the goroutine may thus close the channel after having sent the response)?

	==> Consider callee S+Y can be defined for both coroutines and goroutines?

		f(x) { yield} expands to:	callee::yield —> message: ?? —> caller::resume

		coroutine::yield + subroutine::resume

			==> Works if we can define what message::?? carries?
			==> For yield = await (yield back to caller while waiting for a future event) we need message: future<x> (something the caller can recognize as not yet available)?
			==> For yield = yield y (yield a value back to caller) we need message: y (something the caller can recognize as one value with more to come)?

		==> goroutine::yield + subroutine::resume

			==> Works the same ways as for coroutine above (but the messaging must be made over the response_channel using messages that encode a value or a future value)?
			==> It seems here coroutines and goroutines differ only in the message scheme?
