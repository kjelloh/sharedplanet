	Peer A::f 	—> 	Peer B::operation
		<— Future<B::operation::result> <— 

	==> When Peer B calls Peer A it returns a Future return value that must be kept alive until the asynchronous execution initiated by the call ends.

	Peer A::operation 	<— 	Peer B::f
		—> Future<A::operation::result> —>

	==> Let A::f be a user interface control (e.g. a button) and A::v is a user interface view (e.g. the Button Caption).
	==> Let B::o be some asynchronous operation returning a Future<B::o::r> (a future result)
	==> Let A::f call B::o (e.g. on button click)

	Peer A::f 	—> 	Peer B::o
		<— Future<B::o::r> <—

		==> Consider B::o to create and return an explicit view B::o::v of that very call?
		==> Let B::o::v aggregate and own the future result Future<B::o::r>?
	==> Now, who would own and delete the created operation view B::o::v?
		==> It seems B::o::v can’t delete itself (as it must be its owner that deletes it)?
			==> If B::o::v is controlled by an std::unique_ptr (or similar) it is evident B::o::v can’t delete itself as this would confuse owning std::unique_ptr<B::o::v>)?
		==> It seems it is complicated for A to own B::o::v (A would have to delete correct B::o::v on some dispatched event from B::o)?

1) Consider to understand the Windows Message loop?

	==> This seem to be a good wiki book on Windows Message Loop (https://en.wikibooks.org/wiki/Windows_Programming/Message_Loop_Architecture <https://en.wikibooks.org/wiki/Windows_Programming/Message_Loop_Architecture>)?

	==> This seem to be the microsoft official specification (https://msdn.microsoft.com/en-us/library/windows/desktop/ms644927(v=vs.85).aspx)? <https://msdn.microsoft.com/en-us/library/windows/desktop/ms644927(v=vs.85).aspx)?>

		==> It seems a Console application simply calls the system for input and output whilst a Windows program is event driven (waits for input)?

	”Unlike MS-DOS-based applications, Windows-based applications are event-driven. They do not make explicit function calls (such as C run-time library calls) to obtain input. Instead, they wait for the system to pass input to them.”

		==> it seems each windows is called (its windows procedure) by a ”message dispatcher” to act on events adressed to it?

	”The system passes all input for an application to the various windows in the application. Each window has a function, called a window procedure, that the system calls whenever it has input for the window. The window procedure processes the input and returns control to the system."

		==> Calls to a windows procedure may be asynchronous (Post) or synchronous (Send)?

	”The system uses two methods to route messages to a window procedure: posting messages to a first-in, first-out queue called a message queue, a system-defined memory object that temporarily stores messages, and sending messages directly to a window procedure."	

		==> It seems a windows GUI can in fact be multi-threaded ?

		”The system maintains a single system message queue and one thread-specific message queue for each GUI thread.”

		==> It seems message dispatching is made first from System Message Queue to GUI Thread Message Queues and then by each thread?

		”The system removes the messages, one at a time, from the system message queue, examines them to determine the destination window, and then posts them to the message queue of the thread that created the destination window. ”

		==> It seems an application must implement at least one Message Queue (in WinMain for single-threaded) and in each GUI-thread (multi-thrteaded)?

		”An application must remove and process messages posted to the message queues of its threads. A single-threaded application usually uses a message loop in its WinMain function to remove and send messages to the appropriate window procedures for processing. Applications with multiple threads can include a message loop in each thread that creates a window.”

		==> It seems each Message Loop just do dequeue, translate and dispatch for each message in the queue?

2) Consider that most front-ends are single threaded which would suggest they should (and do) implement the Reactor Design Pattern?

	==> It seems a Windows Application in fact implements the Proactor Design Pattern?

		==> The System unqueues messages and posts them (asynchronous dispatch) to correct GUI-Thread queue?

			==> The System is then the ”Proactive Initiator”?
			==> The Windows Application is the ”Asynchronous Operation Processor”?
